# 建议与采纳

进入建议模式、处理用户对建议的反馈，或需要向应用交接结构化建议时读取。默认交付供人阅读的建议；只在用户或宿主明确需要时输出 JSON。

## 原文与建议分开

以本次实际读取的完整原文为底稿。保留正文、段落顺序、标点、代码、链接、元数据和既有格式，不把新增标记直接写进原稿。必要时另存只读快照；不能用上次生成稿替代用户当前版本。

建议从全文问题到局部表达组织，先列影响理解或操作的事项，再列可选优化。优先级表示影响程度，置信度表示判断依据强弱，两者不同。不预测流量，不用主观偏好冒充逻辑错误。

供人阅读的结果先给简短总览。同类标题或样式调整可在一张表内列出独立编号、位置和变化，共用一次理由，避免多张内容相同的长卡片。提供 JSON 时，把完整操作锚点放在 JSON，人读版保留能辨认的原句和必要上下文，不必重复整块配置或同一段解释；不得因此把独立动作合成只能整体接受的一项。

## 逐条建议

每条建议有稳定编号，如 `S01`，包含：

- **位置与原文**：章节名及准确引文。跨段衔接同时引用前段末句、后段首句；重复文字加相邻上下文，保证能唯一定位。展示时可以节选，但实际操作锚点必须完整、准确，不能含省略号代替原文。
- **类型与优先级**：移动、替换、删除、拆段、合并、标题层级或强调；缺材料的事项标成待澄清或待核验。没有必要不另加数字评分。
- **理由与效果**：具体是哪一处理解、指代、条件或层级问题，调整后改善什么。审美选择如实标成可选，不只写“更有逻辑”“更有传播力”。
- **拟议变化**：替换给出“原句 → 建议句”；删除保留待删原文；移动给出完整移动范围和准确目的地，并展示两处受影响的上下文；强调给出原句中的准确片段、呈现形式和作用。拆段、合并不顺带改字。
- **依赖与状态**：需要一起处理的动作合成一项，或注明依赖、互斥编号。初始状态为待选择；用户可采纳、忽略或自行调整建议。待澄清项只说明所缺材料，不提供假定事实后的可执行替换。

此外，简要说明值得**保持不动**的结构、原句或细节及理由。没有问题就说清楚，不为凑数添加修改。不同主题不必压成单一主张。

不要仅把整篇改稿后的差异机械拆成卡片：先形成可解释的编辑动作，再检查它在上下文中的效果。纯粹换皮或意义相同的反复改写不值得列入。

效果必须由该项实际动作产生。例如只给文末条件加粗，不会让它在前面的操作之前出现，不能声称已让读者提前看到；需要提前呈现时，应另提移动或就近提示，并明确相应范围和依赖。

## 采纳与后续反馈

- 用户明确选择编号后，只应用该项及已经获准的依赖项；“采纳 S02”不授权其他建议。选择缺少前置项时，说明具体依赖，等待用户选择，不自动扩展。
- 采纳前重读当前原文，核对锚点与上下文；原文变化导致建议过期时，重新定位和评估受影响的项。不能沿用失效偏移，也不能靠相似文字猜位置。
- 默认另存包含已采纳变更的稿件。应用、预览、撤销、忽略分别记录，不把预览当成已应用；复制和导出以用户选定的正式版本为准。
- 已忽略项不在下一轮自动复活；用户改写过的文字保留。新建议使用新编号，原编号不悄悄换成别的修改。调整同一项时保留其修订关系。
- 应用后重读修改处及其前后；移动同时检查移出与移入位置。仅撤销指定改动，不覆盖用户后来所作的编辑；无法可靠分离时说明冲突，不整篇回滚。
- 网页应在独立建议状态与预览副本中呈现变化，用户采纳后才通过编辑器操作写入。安装本 Skill 不等于网站已接入；这里只定义交付和行为，不声称提供了应用、存储或撤销引擎。

## 结构化交接（按需）

需要机器读取时，用以下字段交接同一组建议，供宿主验证和呈现。原文摘要不能替代完整底稿；版本值必须来自宿主或文件工具，不能由模型编造。

```json
{
  "source_sha256": "由工具计算的原始文件字节 SHA-256",
  "suggestions": [
    {
      "id": "S01",
      "kind": "replace",
      "priority": "medium",
      "confidence": "high",
      "anchor": {"quote": "原文中的完整待改片段", "prefix": "", "suffix": ""},
      "proposal": "拟议替换文本",
      "reason": "具体问题与改善",
      "move_target": null,
      "presentation": null,
      "depends_on": [],
      "conflicts_with": [],
      "status": "pending"
    }
  ],
  "keep": [{"quote": "原文中建议保持的准确片段", "reason": "保持理由"}]
}
```

- `source_sha256` 绑定实际读取的 UTF-8 文件原始字节，由工具计算。交互输入未建立文件时，此字段可为 `null`，另加 `source_revision`，填写宿主实际提供的版本标识；两者都无法取得时，只交付供人阅读的建议，不伪造版本或输出可执行交接。
- `kind` 使用 `replace`、`delete`、`move`、`split`、`merge`、`heading`、`emphasis` 或 `clarify`。`priority`、`confidence` 分别为 `high`、`medium` 或 `low`；置信度不是保证正确的概率。
- `anchor.quote` 是源文中的精确连续文本，重复时通过紧邻的 `prefix`、`suffix` 消除歧义。移动锚点覆盖完整移动段落，不能只标出开头后让宿主猜范围；其他操作同样给出完整作用范围。
- `move_target` 在移动时包含目标 `anchor` 和 `placement`（`before` 或 `after`），其他类型为 `null`。目的地不得位于待移动内容内部。移动 `proposal` 为 `null`，需要改连接句时另列依赖或向宿主交付明确的组合动作，不能把整篇新稿藏进移动项。
- `replace`、`split`、`merge`、`heading` 的 `proposal` 是拟议 Markdown；`delete` 为 `""`，`clarify` 为 `null`。强调的 `proposal` 为 `null`，通过 `presentation` 给出 `bold`、`highlight` 或 `standalone`；其他类型的 `presentation` 为 `null`。强调锚点本身就是准确强调范围，不更改文字。
- `clarify` 用 `reason` 说明需要澄清或核验的具体信息，不能直接应用。`keep` 不属于待采纳的修改。
- 依赖和互斥引用真实编号，依赖不得成环。重叠范围需明确为互斥，或形成有顺序、能重新核对锚点的依赖；不能默默覆盖先前采纳的改动。
- `status` 初始为 `pending`。只有用户选择后才能记录 `accepted` 或 `ignored`；实际写入成功后才标为 `applied`，过期或缺少依赖时标为 `blocked`。生成和展示预览不改变采纳状态。
- JSON 只描述建议；宿主应校验版本、唯一锚点、范围、依赖和用户选择后再应用。不执行模型返回的代码或任意操作，不能直接拿整篇模型输出覆盖正文。

交付前核对 JSON 与可读建议的编号、原文、动作和状态一致。此契约不替代宿主的数据校验与编辑器集成，也不证明建议已被执行。
